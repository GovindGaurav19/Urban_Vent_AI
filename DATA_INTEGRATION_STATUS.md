# Data Integration Status

Status snapshot for this build. Provider requests are wired through the Node backend, but the build container could not resolve external provider domains. Browser-side integration has therefore been tested with deterministic mocked responses; actual live upstream reachability must still be confirmed from the target network/deployment.

| Source / capability | Status | What the application shows | Remaining limitations / required work |
|---|---|---|---|

## Data timestamp contract

- **Model/observation time:** time supplied by the provider for its returned environmental product; never substituted with the fetch time.
- **Fetch time:** timestamp at which the application requested and received the provider payload.
- **Freshness:** derived from the provider's model timestamp where available. A successful request alone does not make the environmental product fresh.
- **Observed versus modelled:** weather and CAMS outputs are labelled as model products. No source is labelled a connected municipal sensor or direct monitor.
- **Timestamp interpretation:** the displayed environmental product time is the provider-supplied model valid/current timestep, not an independently verified model-initialization/run timestamp. The API fetch time is tracked separately; a fresh fetch does not make an older valid timestep fresh.

No provider request from the preparing environment could be verified end-to-end over the public internet. The adapter response parsing, HTTP proxy routing, input validation, caching, state labels and timestamp separation are covered by tests using mocked provider responses.
